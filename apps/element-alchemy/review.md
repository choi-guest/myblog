## 3. 발견한 문제

### 문제 1 — [중간] 이동 애니메이션 중 [새 게임]을 누르면 이전 게임 타일이 판에 남음
- **위치**: `js/main.js:120`(`await renderer.animateTurn(...)` 뒤에 게임이 바뀌었는지 확인하지 않음), `js/render.js:144-146`(대기 후 오래된 `state`로 `syncBoard`), `js/game.js:199`(`newGame()`이 `nextId`를 1로 되돌려 이전 게임과 새 게임의 타일 id가 겹침)
- **재현**: 이동 직후 130ms 안에 [새 게임]을 클릭합니다. 브라우저에서 재현했습니다. 점수 0·턴 0·도감 0/11인데 판에는 이전 게임 타일 9개가 그대로 그려졌습니다. 실제 상태는 타일 3개라서 화면과 aria-label이 모두 틀립니다. 다음 이동 때 다시 맞춰집니다. 이전 턴이 승리나 게임 오버를 일으킨 턴이었다면, 새 게임이 시작된 뒤에도 그 결과 대화상자가 뜰 수 있습니다(main.js:122-129).
- **제안**: main.js에 게임 세대 번호(`let generation = 0`)를 두고 `startNewGame`에서 1씩 올립니다. `runTurn`은 시작할 때 값을 저장해 두고, `await` 뒤에 값이 달라졌으면 바로 반환합니다. 또는 `renderer.reset()` 때 진행 중인 애니메이션을 취소합니다. `nextId`를 게임마다 초기화하지 않는 것도 보조 대책이 됩니다.

### 문제 2 — [중간] 한글 입력 상태에서 WASD가 동작하지 않음
- **위치**: `js/input.js:29-30`
- **재현**: Windows나 macOS에서 한/영 키로 한글 입력으로 바꾼 뒤 W를 누릅니다. `event.key`가 `'ㅈ'` 또는 `'Process'`로 들어와 `KEY_MAP`에 없으므로 무시됩니다. 한국어 블로그 방문자는 한글 입력 상태인 경우가 많습니다. 방향키는 정상입니다.
- **제안**: `event.code`(`KeyW`/`KeyA`/`KeyS`/`KeyD`)로 판정하거나 `event.key`와 함께 확인합니다. `event.isComposing`일 때도 `code`로 처리합니다.

### 문제 3 — [낮음] 안내 문장 구두점 "발견!," 어색함
- **위치**: `js/render.js:240`, `248`
- **재현**: 한 턴에 발견과 다른 반응이 함께 일어나면 "폭풍 Ⅰ 발견!, 증기 Ⅰ 변성."처럼 읽힙니다(브라우저에서 확인).
- **제안**: 각 항목 끝의 "!"를 빼고 문장 끝에만 붙이거나, 항목을 마침표로 나눕니다.

### 문제 4 — [낮음] 같은 안내 문장이 반복되면 스크린 리더가 다시 읽지 않을 수 있음
- **위치**: `js/render.js:202-204`
- **재현**: 막힌 방향을 연속으로 누르면 같은 텍스트가 같은 노드에 다시 들어가 일부 스크린 리더가 무시합니다.
- **제안**: 텍스트를 비운 뒤 다음 프레임에 다시 넣거나, 끝에 보이지 않는 변화(예: 줄바꿈 없는 공백 토글)를 줍니다.

### 문제 5 — [낮음] 대화상자 배경 색이 CSS 변수가 아님
- **위치**: `style.css:551` `rgb(0 0 0 / 0.5)`
- **제안**: CLAUDE.md의 "모든 색상은 `:root` 변수" 규칙에 맞게 `--backdrop` 변수로 뺍니다.

### 문제 6 — [낮음] `100vw` 기반 폭과 `body { overflow-x: hidden }`
- **위치**: `style.css:111`, `199`, `248`, `278`, `418`
- **설명**: 일반 스크롤바가 있는 데스크톱 브라우저에서 창 폭이 약 530px 미만이면 `100vw`에 스크롤바 폭(약 15px)이 포함됩니다. 그러면 판 오른쪽이 스크롤바 폭만큼 잘리거나 오른쪽 여백이 16px보다 작아집니다. `overflow-x: hidden`이 이 넘침을 가려서 가로 스크롤 검사로는 드러나지 않습니다. 모바일(오버레이 스크롤바)에서는 문제없습니다.
- **제안**: `min(100%, 480px)`처럼 부모 기준 폭을 쓰고 `overflow-x: hidden`을 제거합니다.

### 문제 7 — [낮음] 768px 폭에서 도감 열이 좁음
- **위치**: `style.css:584-589`
- **설명**: 768px에서 오른쪽 열이 209px라 도감 항목 하나가 약 100px입니다. 그래서 "바람 + 불" 같은 힌트가 줄바꿈됩니다(스크린샷 확인). 기능에는 문제없습니다.
- **제안**: 두 열 전환 기준을 900px 정도로 올리거나, 좁은 두 열 구간에서는 도감을 1열로 표시합니다.

### 문제 8 — [낮음] 테스트용 `setBoard`가 공개 API에 노출됨
- **위치**: `js/game.js:313-320`
- **설명**: 테스트에는 유용하지만 게임 오버 상태를 되돌릴 수도 있습니다. 화면에서 호출하는 곳은 없습니다. 이름을 `_setBoardForTest`로 바꾸는 식으로 의도를 드러내는 것을 권합니다.

## 4. 확인하지 못한 항목과 이유

- **실제 승리·게임 오버까지의 브라우저 플레이**: main.js의 `game` 인스턴스는 모듈 내부에 있어 javascript_tool로 판을 조작할 수 없었습니다. 대신 로직(Node), `showDialog` 동작(브라우저), main.js 흐름(코드)을 따로 확인했습니다. 코드상으로 승리 [계속하기]는 판으로 포커스를 돌리고, 승리와 게임 오버가 같은 턴에 나면 승리를 닫은 뒤 게임 오버 대화상자를 띄우며, 게임 오버 대화상자를 Esc로 닫으면 판이 멈추고 [새 게임]만 가능합니다. 모두 명세와 맞습니다.
- **`prefers-reduced-motion` 에뮬레이션**: 브라우저 도구가 지원하지 않아 CSS·JS 코드로만 확인했습니다.
- **실제 터치 스와이프**: `PointerEvent`(pointerType touch)를 직접 보내는 방식으로 확인했습니다. 실기기 확인은 하지 못했습니다.
- **참고**: 브라우저 검증 중 사용자가 같은 탭에서 함께 조작해 일부 수치(턴·점수)는 사용자 조작이 섞여 있습니다. 판정에 쓴 값은 직접 넣은 입력 전후를 비교해 확인했습니다. 문제 1을 재현하느라 진행 중이던 게임이 새 게임으로 바뀌었습니다.

### 새로 생긴 문제
- **A. [낮음] 두 열 전환 기준이 승인된 명세와 다름**
  - 위치: `style.css:585`(`min-width: 900px`), `spec.md:120`(`min-width: 768px`), `review-brief.md:17`("768px 이상 두 열")
  - 설명: fix-brief가 허용한 수정이지만, 768~899px(태블릿 세로 등)에서는 명세와 달리 한 열로 보입니다. 기능과 접근성 문제는 없습니다.
  - 제안: 사용자 확인을 받아 spec.md 4장과 review-brief를 900px로 갱신합니다. 또는 768px를 유지하고 768~899px에서만 도감을 1열 목록으로 바꿉니다.
- **참고 (문제 아님)**: 안내 문장에서 발견·도감 완성 문구가 일반 반응 뒤로 모여 나오므로 실제 반응 순서와 다를 수 있습니다. 읽기에는 자연스러워 그대로 두어도 됩니다.
- **회귀 없음**: 세대 번호·epoch 때문에 버퍼 입력이나 승리·게임 오버 흐름이 깨지는 경로는 코드상 없습니다. `reset()`은 `startNewGame()`에서만 불리고, 그때 세대 번호도 함께 오르며 `busy`와 `pending`도 초기화됩니다.
